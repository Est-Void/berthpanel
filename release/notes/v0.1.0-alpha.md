# berthpanel v0.1.0-alpha

The first public alpha. It is honest about what it is: a small, local-first,
no-root deploy panel for a host you already run, useful today *if* you verify
the parts it cannot verify for you. Read the known limitations before you rely
on it.

## What it is

berthpanel deploys a GitHub project to a hardened systemd **user** unit, with
no root and no Docker daemon, on the machine you already have.

It is **bring-your-own-first**: paste a public GitHub URL, review the draft
recipe the detector produces, correct what it guessed wrong, and deploy. A
small starter catalog (Memos, Filebrowser, Gitea, Uptime Kuma) ships as a
convenience, not as the product — it is frozen for this release.

## Headline features

- **Deploy a GitHub URL to a hardened systemd user unit.** The wizard resolves
  the commit, detects the build, and shows a draft; on confirm the panel
  clones, builds in a sandbox, writes a `berthpanel-<name>` user unit, and
  registers the service on an assigned loopback port.
- **Allowlisted egress, logged.** Every outbound request passes a compile-time
  host allowlist, per hop, with no redirect following, and is appended to
  `net.log`. The exact list is printed by `berthpanel --show-endpoints`. There
  is no telemetry.
- **`--selftest`.** An end-to-end check that renders, writes and starts a
  uniquely named, loopback-only unit through the real `systemctl --user` path,
  then removes it and checks for leftovers. It needs a live user manager.
- **`make check`.** A read-only gate (clang-tidy over `src/` plus the test
  suite) that changes nothing in the tree.
- **Backup and restore.** `berthpanel backup <service>` / `restore` pack and
  unpack a service's data directory and its 0600 secrets file in one archive.
- **Guides for reachable services.** Managed Caddy for TLS and a documented
  Tailscale-only access profile, both keeping the service on loopback.
- **Recipe editing.** A detected `start_cmd` is only a heuristic; fix it with
  `berthpanel __recipe-edit <service> [--start-cmd ... --port ... --memory ...
  --tasks ... --health ... --name ... --description ...]` from the CLI, or
  with `E` on a user recipe in the panel. Builtin catalog entries are
  read-only; create a user recipe to override one.

## Install

`install.sh` is the primary path. It is verify-first and fails closed: it
checks the release's `SHA256SUMS` against a minisign signature before
installing anything, verifies every artifact's checksum, never runs `sudo`,
and never installs a system package.

```sh
# Verify first, then run — never pipe an unverified script straight to sh.
minisign -Vm SHA256SUMS -p release.pub
sha256sum --check --strict SHA256SUMS
sh install.sh --source . --pub release.pub
```

Uninstall is the same script (`sh install.sh --uninstall`). It removes only
`berthpanel-`-prefixed user units and the binary, and leaves your data under
`~/.local/share/berthpanel` in place.

From source:

```sh
make            # debug build   -> build/debug/berthpanel
make release    # release build -> build/release/berthpanel
```

Run `berthpanel --selftest` after installing to confirm your user manager
works.

## Known limitations (alpha)

- **github.com only.** The source front door accepts an https GitHub URL and
  nothing else. Other forges are not supported in this release.
- **Public repositories only.** The wizard resolves pins without a token, so a
  private repository cannot be deployed.
- **Toolchains are limited to `bun`, `pnpm`, `go` and `python3`.** They must
  already be on `PATH`; the alpha does not auto-provision a toolchain into the
  build sandbox.
- **A detected `start_cmd` is a heuristic.** The stack detector rewrites the
  start command from the repository's own files, and it can be wrong — a
  service can deploy successfully and still never answer. Verify it after the
  first deploy and correct it with `__recipe-edit` (or `E` in the panel).
- **The builtin catalog is frozen at wave 1** (Memos, Filebrowser, Gitea,
  Uptime Kuma). Later waves are not planned for v1; add your own project as a
  user recipe instead.
- **Single-unit services only.** A recipe describes one systemd user unit.
  Multi-process stacks (for example an app plus its database) are out of
  scope for v1.
- **Uninstall does not purge data.** Removing a service stops and unregisters
  it but leaves its data directory under `~/.local/share/berthpanel` for you
  to delete.

The sandbox is a blast-radius reducer, not a trust boundary: builds run as
your own user. See the trust model in `README.md`.
